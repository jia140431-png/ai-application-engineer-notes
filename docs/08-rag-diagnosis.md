# RAG 排查案例：从猜组件到找证据

[返回目录](../README.md) · 来源：原对话复盘 + 补充整理。

## 原回答的有效起点

用户提出先查 Git 变化、用 Golden Dataset 比较历史表现，再按问题查询 Trace。这体现了变更、回归与可观测性意识。需要修正的是：Git 不是全部变化来源；证据没进 Prompt 不一定是重排问题；证据进了 Prompt 仍答错也不一定是模型服务故障。

## 可重复的排查步骤

1. **界定范围**：是一个问题、某类问题、某租户，还是所有请求？区分历史一直不支持与新发生的回归。保存实际请求时间和身份条件。
2. **列变化**：代码、Prompt、模型标识和参数、Embedding、索引、文档及权限、检索阈值、解析器、用户问题分布。无代码发布也可能退化。
3. **建立复现**：使用相同问题和权限上下文；记录每个组件版本。外部模型无法完全固定时说明限制，并做多次重复观察。
4. **回归与分组**：跑历史 Golden Dataset，并单独加入真实失败案例；避免把所有结果混成一个平均数。
5. **逐层比对**：找到正确证据首次缺失或被误用的位置。
6. **隔离与修复**：一次改变一个主要变量，比较质量、延迟、成本与权限边界。修复后完整回归，灰度观察并保留回退方案。

## 阶段证据表

| 观察 | 下一步核验 | 不能直接推断 |
|---|---|---|
| 原文没有所需事实 | 语料覆盖与数据更新 | 模型能力不足 |
| 原文有、解析后没有 | OCR、表格结构、清洗 | 向量模型不好 |
| 片段有、候选没有 | 改写、过滤、Embedding、索引 | Reranker 不好 |
| 候选有、重排后没有 | 评分与截取规则 | 生成模型问题 |
| 重排有、Context 没有 | 去重、权限、预算与组装 | 必然是重排问题 |
| Context 有、回答错 | 冲突、适用条件、位置、Prompt 与生成约束 | 必然是供应商模型故障 |

最小隔离实验：固定同一个问题、正确证据和输出规则，构造短 Prompt。最小场景答对而完整场景答错，应重点检查上下文干扰；最小场景仍错，再检查问题理解、证据是否充分、模型与参数，并做跨模型对照。实验是缩小范围，不能单凭一次结果断言因果。

## 证据冲突演练

假设两份虚构业务资料分别写“满足条件 X 才可申请”和“某类员工享有一般权益”，模型直接回答“该员工可以申请”。本案例只讨论证据推理，不作为劳动权益或法律结论。

应检查：X 是否已满足？第二段是否足以覆盖该具体事项？文档是否同版本、同对象？是否缺失更高优先级规范？不能把一般权益推断成特定资格成立。

更稳妥的输出是指出缺失条件与资料歧义，提供引用，并请求补充或进入人工核验。系统侧增加冲突及无答案样本；将版本、适用范围和证据优先级作为可信元数据；评估过度确定回答率，而非只看是否输出了一段流畅文本。

## 纸上演练

为同一问题准备四条 Trace：证据未入库、召回后被重排丢弃、组装时截断、证据齐全但存在条件冲突。分别写出“已知证据、仍未知、下一项实验、修复成功标准”。能区分这四类，比背更多框架名称更有助于面试表达。
