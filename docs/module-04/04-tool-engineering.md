# 模块 04 · 第四讲：Tool Engineering——让 Agent 安全可靠地使用工具

[总目录](../../README.md) · [模块目录](../04-agent-tools.md) · [上一讲](03-planning.md) · [下一讲：Memory](05-memory-context.md)

**来源**：原聊天第四讲正文、执行器设计、权限演示和 4 道检验；2026-11-06 核对。本文围绕业务契约重写，原课 Java 代码转为职责说明；新增推演单独标记。

## 1. Tool 不应机械等于 API

内部 API 面向程序集成，Agent Tool 面向模型决策。一个 HTTP 路径可能过于底层，模型要理解多种内部 ID 与规则；一个万能 `handle_everything` 又可能隐藏过多能力。

原课把设备查找、报警查询、维修历史、准备申请、提交已批准工单分别封装。准备与提交分开，是为了使副作用和审批边界清晰，不代表只凭工具名称就能强制控制。

好的工具应围绕稳定业务能力，职责清楚，输入易识别，前置条件明确，返回值能帮助后续行动。粒度需在控制清晰与调用开销之间权衡。

## 2. Schema 是说明书，也只是第一道校验

`query(id)` 无法说明查什么，id 属于哪种实体。原课改为有明确用途的报警查询，规定全局设备 ID、开始结束时间及参数约束。

工具定义至少说明名称、适用场景、输入语义、类型与结构限制。再补充是否只读、结果含义、错误及分页等行为契约，帮助模型避免误用。

字段结构正确不代表业务正确。例如用户要最近 24 小时，模型给出合法的一个月范围；或者设备 ID 格式合法，却属于另一租户。服务端仍要验证范围、权限、最大窗口与结果数量。

**补充解释：**Schema 中的日期格式约定也不自动处理时区、起止顺序和未来日期。应将结构解析与业务条件拆开，不把“JSON 能解析”作为可执行标准。

## 3. Registry、Selector、Policy、Executor

| 组件 | 负责什么 | 不应替代什么 |
|---|---|---|
| Registry | 工具定义、版本和处理器 | 实时业务授权 |
| Selector | 为当前任务选择候选能力 | 后端资源权限 |
| Policy | 校验当前操作是否允许、是否需审批 | 真实业务执行 |
| Executor | 受控调用、异常转换、审计与状态 | 模型的业务目标理解 |
| Result Adapter | 统一 Observation 结构 | 凭空创造真实结果 |

面对 100 个工具，应先按任务发现相关能力，再按可信身份与策略收窄。模型看到工具并不代表调用必被放行；执行时仍要校验当前条件。

**新增例子：**故障调查只开放读台账、报警、维修与知识检索。准备维修申请可以是另一个授权阶段；删除设备与全量客户导出不因语义上“可能相关”而获得权限。

## 4. 执行生命周期

```mermaid
flowchart LR
    A[解析工具与版本] --> B[结构及业务参数校验]
    B --> C[可信身份 资源与审批核验]
    C --> D[持久化操作意图]
    D --> E[真实业务调用]
    E --> F[归一化结果]
    F --> G[保存状态与审计]
```

图是职责示意，不表示远程业务写入和本地日志在同一事务内完成。执行前后的失败窗口必须额外处理。

可信身份由认证系统建立，不让模型通过 `tenant_id=admin` 自行选择权限。工具参数可以包含目标设备，但访问资格应来自可信上下文和业务系统核验。

## 5. 错误语义决定后续行为

原课建议区分 SUCCESS、VALIDATION_ERROR、PERMISSION_DENIED、BUSINESS_REJECTED、TEMPORARY_FAILURE、UNKNOWN_OUTCOME。这是教学状态定义，不是某框架统一枚举。

| 状态 | 含义 | 处理方向 |
|---|---|---|
| 参数不合法 | 请求没有满足契约 | 有界修正，不无限重试 |
| 权限拒绝 | 当前身份不可执行 | 阻断，不换参数绕过 |
| 业务拒绝 | 对象状态或业务规则不允许 | 说明原因或进入其他合法流程 |
| 暂时失败 | 可恢复的服务问题 | 按预算退避或熔断 |
| 结果未知 | 下游可能已经生效 | 查询操作状态，避免重复副作用 |

Observation 需保留工具、请求关联、状态、必要数据与可判读错误。向模型提供下一步所需内容，完整原始响应可留在受控存储中，不必全部进入上下文。

## 6. 消息去重与操作幂等是两层

同一用户消息重复到达，会导致重复任务；同一任务的工具超时重试，又可能重复创建工单。入口与业务执行都需要控制。

原课关系为 `message_id → task_id`，以及 `task_id + logical_action_id → operation_id`。实际映射必须稳定保存，不能每次重试随机生成新 ID。

操作记录显示已成功，就返回原结果；执行中则查询进度；结果未知先核实；确认允许重试时继续使用原幂等键。稳定 ID 是基础，但下游必须真正识别重复或由业务唯一约束保证不重复生效。

**新增推演：**两个相同 operationId 携带不同金额，不能只按“同键已有成功”忽略参数冲突。应绑定规范化操作参数，并拒绝或按明确版本规则处理冲突。这与审批快照也需要一致。

## 7. 超时最容易被误当成失败

建单数据库已经提交，HTTP 响应丢失，调用方只看到超时。此时“再调用一次”可能重复；“告诉用户成功”又没有核验依据。

应保存 UNKNOWN_OUTCOME，以 operationId 查询权威结果，记录真实工单 ID；支持幂等时同键恢复，无法确认则进入对账或人工处置。模型没有渠道读到真实数据库时，不能靠推理判断成功与否。

429、503 等暂时故障也要按具体接口契约分类。写操作是否安全重试，不仅由 HTTP 状态码决定，还取决于副作用和幂等约定。

## 8. MCP 与本地工具的边界

Function Calling 是模型表达工具意图的机制；MCP 标准化 AI 应用访问外部工具等能力；Registry 管有哪些工具，Runtime 组织决策与执行。

少量本地固定工具可直接调用，多应用共享能力时再评估 MCP。采用标准协议不会自动使工具可靠、安全或适合模型使用。

原课提醒 `readOnlyHint`、`destructiveHint`、`idempotentHint` 等声明是提示，不是可信执行保证。外部 Server 说“只读”不意味着可以跳过实际能力审查和权限控制。协议细节参见[模块 05 第五讲](../module-05/05-mcp.md)。

## 9. 评估不仅看工具能否返回 200

原课指标包括工具选择、参数有效性、执行成功、任务成功、重复副作用、越权执行、未知结果、尾延迟及成功任务成本。

建立错误设备、无权限、503、写入超时、重复消息、过期审批、恶意工具返回等测试环境。平均成功率不能掩盖少数越权或重复危险动作；高影响边界应单独验收。

**补充解释：**“调用成功率”要写清分母，是逻辑调用、每次网络尝试还是整项任务。重试三次终于返回成功，不应在成本和轨迹评估里变成一次无代价成功。

## 10. 原课 4 道自测与解析

1. 企业 100 个 API 应如何提供给 Agent？
2. 参数通过 JSON Schema，是否可直接执行？
3. 建单超时且可能成功，如何恢复？
4. readOnlyHint=true 能保证无写入吗？

<summary>展开答案</summary>

1. 封装清晰业务能力，按任务与权限筛选，不暴露万能超级工具。
2. 不可，还需业务、身份、资源和审批校验。
3. 稳定操作标识查询结果，并按业务幂等契约恢复。
4. 不能，声明是提示，强制边界来自可信执行环境和业务服务。
